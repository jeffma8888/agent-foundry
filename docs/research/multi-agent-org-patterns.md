# Role structures in autonomous multi-agent software frameworks

Multi-agent LLM frameworks disagree sharply on three coupled questions: how many distinct roles a system needs, whether those roles should be fixed up front or chosen per task, and whether adding roles actually produces better software. This brief surveys the major published designs and the empirical evidence on role count, communication overhead, and static versus dynamic team composition.

## Static SOP pipelines: MetaGPT and ChatDev (EVIDENCE)

MetaGPT is the clearest example of a fixed, assembly-line role structure. Its slogan is "Code = SOP(Team)": it encodes Standardized Operating Procedures into prompt sequences and assigns a fixed cast (product manager, architect, project manager, engineer, QA engineer), each emitting a structured artifact (user stories, competitive analysis, APIs, data structures) that the next role consumes ([MetaGPT paper](https://arxiv.org/abs/2308.00352); [MetaGPT repository](https://github.com/FoundationAgents/MetaGPT)). The claimed benefit is that human-like SOPs let agents "verify intermediate results and reduce errors," countering the "cascading hallucinations caused by naively chaining LLMs."

ChatDev keeps the static philosophy but organizes it as a waterfall of four phases (designing, coding, testing, documenting) staffed by chief officers (CEO/CTO/CPO), programmers, reviewers, and test engineers ([ChatDev paper](https://arxiv.org/abs/2307.07924)). Its distinctive mechanism is the "chat chain": each phase is broken into atomic subtasks, and exactly two roles (an instructor and an assistant) hold a context-aware dialogue to propose and validate one subtask. The published run over 70 requirements averaged 17.04 files per program, about 409 seconds, and about $0.30 per program; the paper reports that reviewer-programmer dialogue caught roughly 20 vulnerability types and tester-programmer dialogue caught more than 10 bugs. The value comes from paired propose/validate dialogue, not from a large simultaneous committee.

## Conversational and hierarchical orchestration (EVIDENCE)

AutoGen (Microsoft) drops the fixed pipeline for conversable agents plus a GroupChat manager. The design question it names explicitly is "what agent should be next to speak," and it offers four speaker-selection strategies: round_robin, random, manual (human), and auto (default, an LLM picks the next speaker), plus constrained transitions and custom functions for deterministic "StateFlow" workflows ([AutoGen paper](https://arxiv.org/abs/2308.08155); [AutoGen conversation-patterns docs](https://microsoft.github.io/autogen/0.2/docs/tutorial/conversation-patterns/)). Roles here are not prescribed; the topology is whatever the developer wires.

CrewAI offers both regimes in one framework. Its default is a sequential process (static ordering); its hierarchical process adds a manager agent that delegates tasks to crew members by role and "validates outcomes," emulating a corporate chain of command ([CrewAI hierarchical-process docs](https://docs.crewai.com/en/learn/hierarchical-process)). Tellingly, current CrewAI defaults disable delegation and respect the context window by default, a deliberate retreat from unconstrained agent chatter toward tighter control.

OpenAI's Swarm reduced roles to two primitives, Agents and handoffs: an agent is just instructions plus tools that can "hand off" the conversation to another agent, and the runtime is stateless between calls ([OpenAI Swarm](https://github.com/openai/swarm)). Swarm was explicitly educational and has since been superseded by the OpenAI Agents SDK. Its docs make a subtle point: an "agent" need not be a persona at all, it can represent a single workflow step, so "roles" and "tasks" collapse into the same abstraction.

## Dynamic team composition (EVIDENCE)

AgentVerse is the canonical dynamic-recruitment design. It runs a four-stage loop: (1) Expert Recruitment, which "determines and adjusts the agent group's composition based on ongoing problem-solving progression," (2) Collaborative Decision-Making, (3) Action Execution, and (4) Evaluation, which feeds back to the next iteration and can re-staff the team ([AgentVerse paper](https://arxiv.org/abs/2308.10848)). The paper reports that these dynamically assembled groups outperform a single agent across reasoning, coding, and tool-use tasks, and it observes emergent social behaviors, both helpful and destructive, that scale with group size.

Anthropic's production Research system is a dynamic orchestrator-worker design: a lead agent decomposes a query and spawns a variable number of subagents in parallel, each with its own context window, then a separate CitationAgent handles attributions ([Anthropic engineering](https://www.anthropic.com/engineering/built-multi-agent-research-system)). This is the strongest published pro-multi-agent result: a lead-plus-subagents configuration beat a single agent by 90.2% on their internal research eval. But Anthropic is explicit about cost and scope: multi-agent systems use about 15x the tokens of a chat, token usage alone explained 80% of performance variance on the BrowseComp benchmark, and, critically, they warn that "most coding tasks involve fewer truly parallelizable tasks than research" and that current agents "are not yet great at coordinating and delegating to other agents in real time." They also report role-proliferation failure modes: agents "spawning 50 subagents for simple queries" and "distracting each other with excessive updates."

## Does adding roles improve output quality? (EVIDENCE)

The literature is genuinely split, and two frequently-cited results are often conflated.

"More Agents Is All You Need" shows LLM performance scaling with the number of agents, but the method is sampling-and-voting over identical agents (an ensemble), not a division into diverse roles ([More Agents paper](https://arxiv.org/abs/2402.05120)). It is evidence that redundancy and majority voting help, not that adding a "legal agent" or a "second PM" helps.

The strongest recent counter-evidence is the MAST study, "Why Do Multi-Agent LLM Systems Fail?", which analyzed 1600+ annotated traces across 7 popular multi-agent frameworks and states plainly that these systems' "performance gains on popular benchmarks are often minimal" ([MAST paper](https://arxiv.org/abs/2503.13657)). It derives a 14-mode failure taxonomy in three buckets: system-design issues, inter-agent misalignment (agents acting on conflicting assumptions), and task-verification failures. Misalignment and weak verification, not lack of raw capability, dominate. That directly implicates role proliferation: more roles means more handoff seams where information is lost and assumptions diverge.

## Synthesis (OPINION)

Reading these together, the evidence supports a narrow, conditional case for many roles, not a general one. Multi-agent role structures pay off when the work is genuinely parallelizable and each role explores an independent slice (Anthropic's breadth-first research), or when a paired propose/validate dialogue catches errors a solo agent misses (ChatDev's reviewer-programmer pairing). They pay a real, measured penalty otherwise: token blow-up (Anthropic's 15x), coordination failures (MAST), and conflicting implicit decisions.

For software specifically, the balance tips toward fewer roles and more shared context. Cognition's essay "Don't Build Multi-Agents" argues that parallel subagents fail because "actions carry implicit decisions, and conflicting decisions carry bad results": two subagents building parts of the same program make incompatible assumptions unless they share full traces, so it recommends a single-threaded linear agent with context compression instead ([Cognition](https://cognition.ai/blog/dont-build-multi-agents)). Anthropic reaches the same conclusion for coding independently. Both converge on a rule: a "role" is worth a separate agent only when it needs a separate context window and can act independently; otherwise the seam costs more than the specialization buys.

The dynamic-versus-static question resolves similarly. Static SOP pipelines (MetaGPT, ChatDev) buy determinism and checkable artifacts at the cost of rigidity; dynamic recruitment (AgentVerse) and LLM speaker-selection (AutoGen auto mode) buy adaptivity at the cost of an extra orchestration call, nondeterminism, and the risk of runaway role-spawning. The most robust production systems (Anthropic, and CrewAI's cautious defaults) use bounded dynamism: a variable number of workers under a fixed orchestrator, with hard caps and constrained transitions, rather than a fully open society of agents.

## Implications for an autonomous AI-agent dev org

- Add a role only when it needs its own context window and can produce an independently checkable artifact. If a "designer" or "second PM" just re-reads the same files and comments, fold it into an existing role's prompt: every activation is one model-API call against a shared token budget, and MAST shows the marginal role usually adds a misalignment seam rather than quality.
- Prefer a bounded orchestrator-worker shape over a free society of agents. Anthropic's win came from a fixed lead spawning a capped number of workers; its failures came from unbounded spawning. A kickoff council that sizes a team should emit a hard cap and a fixed allowed-role set, not open-ended recruitment.
- Treat coding as low-parallelism. Both production voices (Anthropic, Cognition) agree coding rarely splits cleanly; a mostly-sequential pipeline (PM to engineer to reviewer to tester to gate) with shared file context beats parallel fan-out for building one coherent codebase. Reserve parallel roles for genuinely independent work (separate services, research, doc generation).
- Since roles have no memory between iterations except files and git, the shared artifact IS the shared context. Cognition's failure mode (conflicting implicit decisions) is amplified when the only handoff is a file: mandate that each role write its assumptions and decisions into the artifact, not just its output, so the next role inherits full traces rather than a bare result.
- Keep the propose/validate pairing; it is the best-evidenced multi-agent win for code. ChatDev's reviewer-programmer and tester-programmer dialogues measurably caught defects. A distinct reviewer and an isolated tester earn their calls precisely because they verify against an independent view.
- Make gates deterministic, not conversational. MAST's third failure category is verification. A release gate that checks "tests pass, artifact exists, diff touches only allowed files" is reliable; a gate that asks an LLM "does this look done?" inherits the failure modes it is meant to catch. Reserve LLM judgment for the second-PM impact/feasibility check, and even there require it to cite specific evidence.
- Budget dynamism against human attention. Dynamic recruitment (AgentVerse) and auto speaker-selection (AutoGen) add nondeterminism a human must eventually audit. Because human attention is the scarcest resource, prefer static team composition per project type plus a small, logged re-staffing rule over per-iteration LLM-driven team changes that are hard to review after the fact.
- Do not confuse ensembling with staffing. "More Agents Is All You Need" scales by voting over identical agents; if you want reliability on one hard sub-decision, run the same role N times and vote, which is cheaper and more checkable than inventing new specialist roles.
